### Balance-cache safety

The denormalised `accounts.balance` nudge (`applyAccountBalanceDelta`) is a
non-authoritative cache; `journal_lines` is the source of truth. In bank
transfer, payroll and deposit refund the nudge is wrapped in `if (created)`, so
an idempotent retry cannot double-count the cache. (Petty cash has no
idempotency key — each movement is a distinct transaction — so its nudge is
unconditional by design.)

## 2. Newly discovered defects and their fixes

### D1 — Cross-tenant delete in `DELETE /api/journal-entries` (security)

The route ran `supabaseAdmin.from("journal_lines").delete().eq("journal_entry_id", id)`
and the matching header delete **with no tenant filter**. The service-role client
bypasses RLS, so any caller holding `accounting.delete` could delete *another
tenant's* journal entry (and its lines) by supplying that id. It also allowed
deleting or rewriting a **system-posted** entry (a sale, purchase, receipt,
payment, payroll run…), silently desynchronising the ledger from its source
document with no reversal to show for it.

**Fix:** the DELETE and PUT handlers now load the row first, scoped to the
caller's tenant (a foreign id resolves to `404 not found`), and refuse any entry
whose `entry_type` is not in the manual allow-list (`manual`, `custom`, and the
screen's own templates). A system entry is corrected by reversing/returning the
document, never by rewriting history here. The header delete is also
tenant-scoped.

### D2 — `/api/invoices` compensation could delete a real posting (data safety)

`createdJournalId` was assigned unconditionally from `postSaleInvoice`. The catch
block deletes `journal_entries`/`journal_lines` for `createdJournalId`. When
`postSaleInvoice` returned `created:false` (a posted `sale_invoice`/`rental_invoice`
already existed for that invoice number — an idempotent retry), a *later* failure
in the same request would enter the catch block and **delete the pre-existing,
legitimate journal entry**, destroying a posted financial record.

**Fix:** `createdJournalId` is now set only when `created` is true, so only a
journal this call actually created may be compensated away.

### D3 — Payroll idempotency keyed by date alone (business correctness)

`postPayroll` matched an existing journal on `(entry_type='payroll',
reference_number)`, and the route defaulted `reference` to `PAYROLL-<date>`. Two
**legitimate** payroll runs on the same date (e.g. a regular run and a
supplementary/bonus run) therefore collapsed: the second run returned the first
run's journal and posted nothing, silently dropping real payroll.

**Fix:** the run reference is now the explicit idempotency key and is **required**
(a missing reference is `400`). The date is no longer used as a key. The payroll
form sends `PAYROLL-<date>-<runId>` where `runId` is stable for the lifetime of a
submission (so a retry after a failed submit is idempotent) and rotates after a
successful run (so a genuinely new run — including a second run on the same date
— posts its own journal). Covered by new tests: two different references on one
date produce two journals; the same reference twice produces one.

### Deploy (rollback-safe)

```
git -C /var/www/speed.harbourconsultancies.com pull --ff-only origin main
npm ci && npm run build          # must exit 0
pm2 restart speed --update-env
```

`git pull --ff-only` guarantees no local work is discarded; the app is only
restarted after a successful build, so a failed build leaves the running service
untouched.

### Post-deploy smoke tests

1. `GET /login` → 200; `GET /dashboard` anonymous → 302 to `/login`.
2. `GET /api/invoices` anonymous → 401.
3. Log in as the company admin → `/dashboard` loads; issue a sale → a balanced
   `sale_invoice` journal appears in `journal_entries`.
4. Retry the same submit → no second journal (idempotent).
5. Record a bank transfer and a payroll run → each posts one balanced journal;
   a second payroll run on the same date with a new reference posts its own.
6. Confirm anon cannot read a protected table (RLS status is a separate,
   migration-dependent check — see §6).

### Rollback

- **Application:** `git -C <dir> checkout <previous-commit>` then
  `npm ci && npm run build && pm2 restart speed --update-env`. A pure code
  rollback is safe because Exec 34–36 changed **no schema**.
- **Do not** restore an old database snapshot over newer data: financial rows
  created after the deploy would be lost. Roll the *code* back, not the data.
- **Never** reverse a migration by hand; use the paired
  `*_rollback.sql` only under operator supervision.
