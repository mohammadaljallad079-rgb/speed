## 3. The invoice API is now the single rental posting path

`POST /api/invoices` (unchanged auth model: `requireContext(request, { module:
"sales", action: "create" })`) now:

- verifies the customer **and** the rental contract belong to the caller's tenant
  (`assertReferences`), so a crafted `rental_contract_id` cannot point at another
  tenant;
- is **idempotent per rental contract** — a retry (double click, network retry)
  returns the existing invoice instead of minting a second invoice + journal;
- **derives** `paid_amount` and `status` from the amounts; a client-supplied
  `paid_amount` cannot contradict the advance the journal posts;
- writes `payment_type` for a rental, so the invoice reads exactly as it did when
  the browser built it;
- on any posting failure **removes the journal (lines + header) and the invoice**,
  so a failed posting leaves no orphan rows.

`extension` is treated as a rental for revenue (41001) and entry-type purposes,
so contract extensions contribute to rental revenue in the same way.

## 5. Tenant isolation (behavioural)

- `assertWritableTenant`: a tenant-A caller may write only tenant-A (or its own
  tenant-less value); writing `tenant-B` throws.
- The rental contract is now written with `tenant_id` resolved from the session
  (`supabase.auth.getUser()` → `users.tenant_id`), never from caller input. On the
  current single-tenant install (no tenant) it stays tenant-less, so the live
  installation is unchanged.
- A `client` role cannot create a sale/invoice (`can()`), an `admin` can.

These are pure-function assertions executed in `tests/exec34-rental-posting-closure.test.ts`.
